# Everloop audit and implementation plan

Reviewed 22 November 2026 against `a72f880` on `main` and revised after a signed-in BotBiz workflow review. The audit findings describe the starting point. The implementation status below records follow-up changes.

Everloop should help a team capture WhatsApp leads, respond while the customer service window is open, run campaigns for people who have opted in, and see which campaigns produce replies and sales. Keep the current Next.js, Supabase and Meta Cloud API foundation. Fix message eligibility, campaign delivery and reporting before increasing send volume. Improve the inbox and add installable mobile access in parallel with campaign development.

## 1. Platform audit

The review covered the application routes, setup and auth, team roles, inbox, contacts and imports, templates, broadcasts, pipelines, dashboard, automations, flows, AI settings and knowledge base, browser notifications, public REST API and MCP interfaces. The current foundation includes account scoping and role checks, encrypted provider credentials, signed Meta webhooks, contact deduplication, message pagination within threads, template lifecycle handling, flow validation, AI handoff and broad unit coverage. The most urgent gaps sit between those features at send time and during recovery.

| Priority | Finding | Impact and evidence |
| --- | --- | --- |
| P0 | Marketing eligibility is missing from delivery | Audience selection supports all contacts, tags, custom fields and CSV. The CRM has no dedicated marketing consent ledger or suppression check in the manual template, campaign or automation delivery paths. A contact can enter a marketing audience without a consent record. [Audience resolution](../src/lib/broadcast-audience.ts#L125), [dashboard send endpoint](../src/app/api/whatsapp/broadcast/route.ts#L70), [automation sends](../src/lib/automations/meta-send.ts#L178). |
| P0 | Tab-driven campaigns can stall or resend | The wizard submits sequential batches and records each result from the browser. Closing the tab or locking a phone can interrupt that work. If Meta accepts a send before the status persists, the recipient may be retried. Manual resume has its own lock. The original wizard does not use it, and API and resume runs use request-bound `after()`. [Wizard delivery](../src/hooks/use-broadcast-sending.ts#L429), [resume lock](../src/lib/whatsapp/broadcast-resume.ts#L63), [public API timeout note](../src/app/api/v1/broadcasts/route.ts#L29). |
| P1 | Free-form eligibility can be wrong or stale | The inbox derives the window from loaded messages using whole-hour arithmetic and recalculates only when its dependencies change. It treats a thread with zero loaded messages as open and can miss an inbound message beyond the loaded page. The shared manual/API send core does not check the window before attempting delivery, and automation and flow paths call Meta separately. [Thread timer](../src/components/inbox/message-thread.tsx#L290), [shared send](../src/lib/whatsapp/send-message.ts#L217), [flow sends](../src/lib/flows/meta-send.ts#L127). |
| P1 | Outbound success can become a retryable-looking error | The shared send core calls Meta before the CRM insert. A failed insert returns HTTP 500 even after successful delivery acceptance. The operator can see an error, resend, and produce a duplicate. Record send intent, reconcile ambiguous delivery, and surface its state in the composer. [Message persistence](../src/lib/whatsapp/send-message.ts#L480). |
| P1 | Inbound processing can fail after Meta receives HTTP 200 | The verified payload runs in `after()` with a request timeout and no durable intake record. A failed insert is logged, and an already-inserted message skips side effects on replay. A crash mid-processing can leave unread, opt-out handling, or flow and AI work incomplete. [Acknowledgment](../src/app/api/whatsapp/webhook/route.ts#L255), [message replay guard](../src/app/api/whatsapp/webhook/route.ts#L730). |
| P1 | Campaign scheduling and draft resume are incomplete | The wizard offers immediate send and a draft, while the schema already exposes `scheduled_at`. Drafts store the audience type and tags but omit exclusions, custom-field rules, CSV and media inputs. The shared delivery path passes body parameters but does not pass the wizard's per-send media override. [Draft persistence](../src/app/(dashboard)/broadcasts/new/page.tsx#L76), [final wizard step](../src/components/broadcasts/step4-schedule-send.tsx), [shared delivery](../src/lib/whatsapp/broadcast-core.ts#L270). |
| P1 | Campaign reporting can misstate reads and replies | A reply increments the read count even if a read event never arrived. Reply matching selects the latest recipient row by creation time and checks a seven-day window. A newer pending or failed row can hide a reply to an older send, and a regular support message can be credited to a campaign. [Counter trigger](../supabase/migrations/005_broadcast_counts_incremental.sql#L55), [reply attribution](../src/lib/whatsapp/broadcast-recipient-webhook.ts#L75). |
| P1 | Framework patch and clean builds need attention | `next` is pinned to `16.4.2`, and the November security release fixes affected versions through `16.4.4` across several advisories with different applicability conditions. Upgrade the framework and matching ESLint config to a verified patched release, starting with `16.4.6` as a candidate. Browser startup aside, the normal build currently depends on fetching Inter. [Package versions](../package.json#L41), [font import](../src/app/layout.tsx#L4), [Next.js security release](https://nextjs.org/blog/november-2026-security-release), [16.4.6 release](https://github.com/vercel/next.js/releases/tag/v16.4.6). |
| P1 | Invite URL can still point at the upstream domain | With no explicit site URL and no accepted request host, an invitation can fall back to `wacrm.tech`. Production should require a validated Everloop origin and report a configuration error when it cannot construct a valid URL. The local worktree also has a pre-existing deletion of the environment example referenced by onboarding docs. Confirm that change before updating setup instructions. [Invite URL resolution](../src/app/api/account/invitations/route.ts#L97), [setup instructions](../README.md#quick-start). |
| P1 | Mobile inbox and installability need work | The web app has a mobile drawer and single-pane inbox. Fixed `100vh` and `h-screen` shells create a risk around mobile keyboards. The window indicator and contact sidebar are hidden at narrow sizes, and key controls are smaller than the proposed 44 px touch target. There is no install manifest, service worker or background Web Push. [Inbox sizing](../src/app/(dashboard)/inbox/page.tsx#L568), [shell](../src/app/(dashboard)/dashboard-shell.tsx#L47), [thread actions](../src/components/inbox/message-thread.tsx#L1005), [notification behavior](../src/hooks/use-browser-notifications.ts#L44). |
| P2 | Inbox list and search will hit scale limits | The inbox loads conversations in one query, filters the returned list in memory and reloads it on reconnect. Unread totals also start by reading conversation rows. This can omit older conversations when the backend caps responses and adds avoidable work on mobile. Contacts already uses paginated queries and the thread paginates messages. [List loading and resync](../src/components/inbox/conversation-list.tsx#L103), [client filtering](../src/components/inbox/conversation-list.tsx#L171), [unread totals](../src/hooks/use-total-unread.ts#L22), [contact pagination](../src/app/(dashboard)/contacts/page.tsx#L122). |
| P2 | AI provider setup is generic and single-config | The existing compatibility adapter can be used to try either requested provider, but the UI requires a URL and model ID and the database stores one active configuration and one chat key per account. Provider switches replace that configuration. Semantic retrieval separately uses an OpenAI embeddings key, with keyword retrieval available without it. [Provider dispatch](../src/lib/ai/generate.ts#L26), [single config](../supabase/migrations/029_ai_reply.sql#L45), [embeddings](../src/lib/ai/embeddings.ts#L9). |

### Consent and webhook recovery pass

- Record WhatsApp marketing permission and its evidence in contact details or via the explicit `whatsapp_opt_in_at` and `whatsapp_opt_in_evidence` CSV columns. Imports report contacts created without a new permission record. Consent is account-scoped and belongs to the exact destination. Existing contacts without evidence start outside marketing audiences at dispatch. The shared template sender rechecks current permission for inbox, API, automation, campaign and resume sends. Verified opt-out replies persist before the inbox runs any bot or workflow for that message.
- Verified webhook receipts persist before Meta receives a successful acknowledgment. Recovery claims a receipt with an expiring lease. The inbound message, unread count, first contact marker and dispatch checkpoint commit together. Recovery retries incomplete data writes and picks up dispatch that never started. A started dispatch is held for inspection if it is unclear whether an external send occurred.
- Dashboard and public API sends reserve an attempt before contacting Meta. Replays with the same request key cannot send again. When acceptance or persistence is uncertain, the API and inbox report that uncertainty, and the server records any known Meta message ID. Ambiguous transport failures preserve attachments that Meta may still need.
- Lint, TypeScript, the production build and all 1,532 tests passed. Migrations 060–062 were exercised in an isolated PostgreSQL runtime against fixtures for tenant isolation, idempotency, webhook lease recovery and atomic message persistence. Apply them to the staging Supabase project and configure the [webhook drain](docker.md#notes) before an end-to-end Meta pilot. The following pass adds the durable campaign worker and callback reconciliation. Real Meta traffic and the staging rollout remain to be verified.

## 2. What can be added

### Keep the existing inbox and approved-template workflow

Scope the initial release to replies in existing conversations and approved-template outreach from Contacts and Campaigns. An inbound customer message opens or refreshes the 24-hour reply window. Show the window status in the inbox and require an open window for free-form sends on the server. For acquisition, a basic click-to-chat link can bring prospective customers into the existing inbox. Ongoing marketing permission is recorded separately from the inbound message. [WhatsApp Business Messaging Policy](https://whatsappbusiness.com/policy/). [WhatsApp click to chat](https://faq.whatsapp.com/5913398998672934).

### BotBiz workflow review

The signed-in review covered channel setup, the campaign creation form and audience selector, Contacts, Team Inbox, Templates, Automations, AI Agents and QR Codes. The campaign and template lists were empty in the reviewed account, so the observations apply to setup and navigation. The Everloop interface should use its own components and visual design.

| Workflow observed | Everloop decision |
| --- | --- |
| Campaign creation puts template, audience, optional schedule and message preview in one flow. | Keep Everloop's guided steps. At review, show the final message, eligible recipient count, exclusion reasons, timezone and scheduled time beside the launch action. |
| Contacts exposes filters, labels, source, assignment and import history. | Add consent source and import results to existing contacts before building new audience tools. Put frequently used combinations behind saved segments. |
| Templates separates approval views and exposes sync. | Surface approval and last sync when choosing a template. Show the provider reason when a template is unavailable. |
| Campaign creation exposes an option to include unsubscribed contacts. | Make suppression mandatory across the UI, API, resume and dispatch paths. Keep that decision out of the operator's campaign form. |
| The product also has a QR library, storefront, booking, groups, calling and additional channels. | Start with a basic inbound link. Put broader features into discovery only after a pilot shows a concrete workflow that needs them. |

### OpenRouter and Google AI Studio

Everloop can build on the existing **OpenAI-compatible API** adapter. Its base URL field can point to `https://openrouter.ai/api/v1` with an OpenRouter key or `https://generativelanguage.googleapis.com/v1beta/openai/` with a Gemini API key created in Google AI Studio. The adapter appends `/chat/completions`. Use an eligible model ID in the provider's catalog and **Test connection** with a synthetic prompt. Both providers document compatible APIs. A real-key test is pending for this application. The existing form stores one choice at a time. [Existing adapter](../src/lib/ai/providers/openai-compatible.ts#L77), [OpenRouter OpenAI compatibility](https://openrouter.ai/docs/guides/features/compatibility), [Gemini OpenAI compatibility](https://aistudio.google.com/docs/openai).

Offer both integrations with stored keys and a free-only filter. Free model availability, capabilities and quotas vary by provider, project and model. OpenRouter's `openrouter/free` can be useful in the playground. Prefer a pinned, evaluated model for live auto-reply so behavior can be tested consistently. Live customer context needs a configuration whose terms allow the intended use. Google's unpaid terms limit sensitive, confidential and personal information and allow use of submitted content for improvement under the general unpaid terms. OpenRouter data handling can vary by the routed provider. Keep unpaid sandbox mode synthetic by default, get an admin to enable a suitable live configuration, and send only the context the reply needs. Free AI usage and Meta WhatsApp message charges are separate. [OpenRouter free router](https://openrouter.ai/docs/guides/routing/routers/free-router), [OpenRouter limits](https://openrouter.ai/docs/api_reference/limits), [OpenRouter privacy and logging](https://openrouter.ai/docs/guides/privacy/provider-logging), [Gemini pricing](https://aistudio.google.com/docs/pricing), [Gemini terms](https://aistudio.google.com/docs/terms).

### Mobile app

Ship a responsive progressive web app first. It uses the existing web app and login, adds an Everloop Home Screen icon and standalone launch, and can support push notifications. Mobile work should prioritize Inbox, Contacts, Campaigns, and approvals. Keep a mobile list or detail view for flows and pipelines, and validate editing where it is practical. Android Chrome and iOS Safari have different install and permission flows. iOS Web Push applies to Home Screen web apps. A native app is a later product decision if App Store distribution or OS-specific capabilities become required. [Next.js PWA guide](https://nextjs.org/docs/app/guides/progressive-web-apps), [WebKit Home Screen Web Push](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/).

## 3. Implementation plan

### 0. Establish a reproducible baseline

- The first implementation pass upgrades Next.js and the matching ESLint config to 16.4.6, bundles the licensed Inter font, and makes invitation URLs resolve to a trusted origin. Test login, password reset, cookies and middleware in staging before any migration to Next.js Proxy. Verify the clean build on the target host using the Node 22 CI baseline.
- Create an isolated staging account and a fixture dataset with two tenants, seeded conversations and recipients, all current team roles, approved and paused templates, and disconnected and connected states. Exercise schema migrations on a fresh database and one populated from representative sanitized fixtures.
- Validate the canonical site URL for invitations and auth callbacks. Keep install files secret-free and reconcile the local deletion of `.env.local.example` with the documented setup.
- Agree release targets from a representative baseline. Record time to open an inbox thread, performance on slower mobile networks, webhook intake lag, campaign queue drain time, unread reconciliation and failure rates. Log account, campaign and attempt IDs without storing credentials or full customer content in operational logs.

**Exit check** — clean production build, passing checks and staging auth and onboarding with the intended domain. Scope any dependency advisory applicability with defensive review of enabled features.

### 1. Enforce reply eligibility and capture marketing permission

- The first implementation pass uses migration 059's `last_inbound_at` for the inbox countdown and server checks in manual sends, API sends, automations, flows and AI replies. Validate existing-account migration coverage in staging. A refused free-form send leaves the contact and thread lists intact. [Inbound timestamp migration](../supabase/migrations/059_dashboard_overview.sql#L75).
- Route inbox, public API, template sends, AI, flows and automations through the same rules. Preserve the existing API contract where possible and introduce typed reasons for an expired window, unavailable template, unsupported destination, opt-out or missing opt-in. Reuse the current Meta adapters, identity handling and status normalization.
- Add account-scoped consent events and suppression with purpose, source, timestamp, proof and operator audit. Treat legacy contacts as unknown for marketing until verified. Enable imports with explicit consent evidence and show duplicate, invalid and missing-consent counts. Handle opt-out keywords and supported template buttons before any bot, flow or campaign follow-up can run. Recheck eligibility immediately before each marketing send and require new permission to resubscribe. Make suppression apply to legacy delivery and recovery endpoints before campaign launch.
- Record outbound intent before calling Meta. Show queued, accepted and uncertain states clearly. Reconcile known Meta message IDs and request timeouts before offering a resend. Persist verified webhook events before acknowledging them, and process retryable stages idempotently. Keep duplicate insert protection while allowing interrupted side effects to resume independently.

**Exit check** — approved-template outreach uses the existing contact workflow. Within-window free-form replies work and attempts at or after expiry stop locally. An opt-out arriving after preflight blocks the recipient's remaining marketing sends. Duplicate, late and interrupted webhook processing recovers without duplicate replies.

### 2. Move campaigns to durable delivery

- Build one server-side campaign service for the wizard, public API and recovery actions. Store the full draft and template ID, language, category, header and button values. Store the segment definition and an immutable launch snapshot with per-recipient personalization. Show excluded counts by reason and a representative final preview. Use the same preflight logic for preview, test send and launch. Validate Meta number health and template eligibility at dispatch.
- Use Supabase Postgres-backed jobs with atomic claims, expiring leases and a scheduler that runs independently of browser sessions. Select a deployment-specific worker after validating supported job cadence and time budgets. Reuse existing recipient rows and message status code. Apply per-sender concurrency, retry backoff and a pause switch. Put ambiguous provider outcomes into reconciliation instead of treating them as safe automatic retries. [Supabase Queues](https://supabase.com/docs/guides/queues).
- Publish real schedule and time-zone handling with UTC storage and a clear preview. Define immediate, scheduled, queued, active, paused, completed with failures and canceled states. Pause and cancel stop pending sends after workers recheck state. Show provider acceptance, delivery, reads, replies and exclusion reasons separately.
- Persist event timestamps independently. Attribute direct replies first via Meta context or linked campaign interactions. Use a clearly labeled time-bounded fallback against the latest eligible send for a contact. Keep unknown attribution and missing read receipts visible. Add comparison by segment, delivery failures, opt-outs, and qualified replies. Build conversion reporting when a booking, deal or commerce event can supply a reliable signal.
- Plan the cutover before enabling the new worker. Existing `sent`, `delivered` and `read` rows remain historical delivery evidence. Review active and ambiguous legacy recipients before importing work into the new queue. Prevent old and new dispatchers from running a campaign simultaneously. Gate new launch by workspace and retain an operator stop switch.

**Exit check** — a campaign survives tab close, duplicate submission, worker restart and Meta rate limits. Its scheduled time and pause state are respected. Paused templates or an opted-out recipient cannot advance. Preview and delivery agree on the template variables and media, and a reply does not manufacture a read receipt.

### 3. Add AI connections and reliable agent behavior

- Add **OpenRouter** and **Google AI Studio** to Settings → AI, with independent, encrypted server-side credentials, fixed endpoints, status and test actions. Reuse the compatibility adapter where model behavior matches and add provider-specific request and response handling where necessary. Migrate existing configurations and preserve the active model and automation settings. Maintain a dedicated legacy custom-endpoint option with its existing validation.
- Add model discovery or a verified catalog with availability, price class and supported modalities. Enforce free-only selection server-side when enabled. Record the provider, resolved model, outcome and usage. On rate limits, show the problem and route to a person or an explicitly approved compatible fallback. Never silently switch a free-only configuration to a paid model.
- Keep keyword retrieval available without an embeddings key. Provider-specific embeddings can come later, with an explicit reindex path and vector dimension checks. Send minimal transcript and knowledge context, apply redaction before supported live calls and distinguish synthetic playground mode. Correct the current UI language about where content is processed. [Current AI settings copy](../messages/en.json#L2133), [chat context](../src/lib/ai/context.ts#L19).
- Ship draft replies first. Pilot auto-reply for FAQ, lead qualification and booking or support routing as part of Everloop's CRM workflow. Keep clear human takeover, stop on opt-out or escalation, and serialize work per conversation so duplicate events and human replies do not race the AI. Test supported languages, uncertain answers, quota exhaustion and handoff in staging before enabling any autonomous customer replies. [WhatsApp Business Messaging Policy](https://whatsappbusiness.com/policy/), [WhatsApp Business Solution Terms](https://www.whatsapp.com/legal/business-solution-terms/).

**Exit check** — an admin can configure both keys, switch between evaluated models, and test each without revealing keys to the browser. Drafting works with or without embeddings. Rate-limit, privacy and expired-window paths reach a human or give an actionable status.

### 4. Rebrand and ship mobile access

- Brand direction — **Everloop** with a compact open-loop E mark formed from one continuous rounded path. Pair a dark evergreen primary color with neutral surfaces and a restrained lime accent. Use the existing Inter typography as the first candidate. Explore a wordmark and an icon before selecting the mark. Test one-color, light and dark, 16 px favicon, 32 px sidebar, and maskable app icon before producing SVG and PNG exports.
- Apply the name and assets to login, navigation, browser metadata, invitations, notification labels, settings and deployment docs across existing locales. Retain MIT and upstream attribution and keep protocol headers and existing preference keys compatible through the rebrand. Use **Campaigns** as the user-facing navigation label while preserving existing routes and integrations.
- Give phones a small set of destinations such as Home, Inbox, Contacts, Campaigns and More. Use one-pane conversation navigation with predictable back behavior, contact details in a sheet, safe-area spacing, dynamic viewport sizing and a sticky composer above the keyboard. Ensure keyboard focus is visible and target 44 px on primary touch controls. Preserve a desktop multi-pane inbox. Use cards for mobile campaigns and a list-based way to update pipeline stages.
- Add a manifest, Home Screen and maskable icons, an installation affordance, a scoped service worker and a clear offline state. Cache public assets only. Keep customer messages, attachments and account data out of service-worker caches. Add opt-in Web Push, minimize lock-screen content by default, revoke subscriptions on logout or membership changes, and check tenant membership on notification deep links.
- Move inbox list and search to cursor-based server queries with indexed filters and a server unread aggregate. Reconcile realtime updates and paginated results on reconnect. Measure first and split heavy route code where the production trace shows a meaningful benefit.

**Exit check** — Everloop installs and opens on iPhone and Android, login and deep links work, the thread stays usable with the keyboard open, and notifications open the correct authorized inbox. Verify compact layouts, keyboard navigation, screen readers, color contrast and media upload on real devices.

### 5. Pilot, measure and expand

- Run a limited staging and production pilot with designated test recipients. Exercise opt-in capture, customer-initiated inbound, a template send, free-form reply, opt-out, campaign schedule, phone and template health, AI draft and human takeover on mobile.
- Report the eligible audience, Meta-accepted and delivered rates, explicit read receipts, direct and inferred replies, opt-outs, first-response time and qualified leads. Define each denominator and separate estimated cost from provider-reported cost. Add attributable revenue when conversion events and deduplication are available.
- Start with one journey for inbound lead qualification or approved follow-up and reuse the existing automation builder. Include exit on reply or opt-out, eligibility and frequency checks, and a test mode. Use pilot results to choose the next feature from saved audiences, referral capture and one conversion event.

**Release gates** — owner, admin, agent and viewer permissions tested across account boundaries. Legacy data and API behavior exercised, including in-flight campaigns and migration rollback with workers paused. Duplicate launch, partial send failure and timeout tests passing. Source and campaign reports reconcile on seeded events. iOS Safari and Android Chrome browser and installed modes tested, including weak network, reconnect, permissions, attachments and voice recording. Monitor webhook lag, pending queues, opt-outs, delivery errors, provider quotas and AI handoff volume during the pilot.

### Sequencing

Finish the foundation and reply-window regression checks first. Complete consent, suppression and webhook recovery before enabling the durable campaign sender. Deliver OpenRouter and Google AI Studio for drafts and testing, then stage the Everloop identity and installable mobile inbox. Enable live campaigns, customer-facing AI and push only after their respective checks pass. Keep the release centered on contacts, templates, campaigns and replies.
